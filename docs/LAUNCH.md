# 原創陸戰 RTS 測試版：發布與正式服務驗收

更新日期：2026-09-30（Asia/Taipei）。這是可執行的驗收清單與營運實驗設計，不表示已建立商品、已驗收正式服務或已發布體驗。程式進度與 Studio 快照見 [ROADMAP.md](ROADMAP.md)，規則及平台調查見 [RESEARCH-2026-09-30.md](RESEARCH-2026-09-30.md)。

首發範圍為原創陸戰 RTS 測試版：村民四資源經濟、施工、時代／科技、兵種反制、最多四方對局、AI 練習、桌面／觸控、新手指引及公平文明主題。海軍、完整歷史文明／戰役、AOE2 全科技樹不列為首發門檻。先通過可玩的首局與公平同步，才進入外部測試；不以功能數量宣稱爆款或完整遊戲。

## 1. 公平商業白名單

使用者要求：**不能 Pay to Win，付費只買文明或造型。** 目前三文明免費，全部共用相同的戰鬥與經濟設定。後續收費內容只能增加外觀或主題收藏，不能增加競技選項優勢。

| 可規劃的商品 | 容許改變 | 必須保持一致 |
| --- | --- | --- |
| 文明主題收藏 | 文明名稱、旗幟、徽記、配色、原創建築／部隊外觀 | 全部資源、成本、人口、施工、訓練、HP、攻擊、護甲、移速、射程、視野、科技、勝利條件與可用命令。 |
| 建築／軍隊造型 | 可辨識的模型裝飾、材質、色彩 | 權威實例、佔地、碰撞、可點選範圍、兵種辨識與重要資訊可見度。 |
| 旗幟／徽記等造型 | 大廳與陣營的個人風格 | 不增加資源、速度、復活、視野、人口、科技、訓練佇列或永久戰力。 |

如果未來出現具有不同戰術、科技樹或單位的文明，所有 PvP／排位玩家都必須能使用相同完整文明池，沒有付費或冗長遊玩門檻。不能只用「數值大致平衡」解釋付費多出的反制選項。第一版文明繼續採同規則、不同身份與外觀。

現在的程式防線如下：

- `CivilizationRules.lua` 只接受文明欄位 `name`、`description`、`emblem`、`accent`、`public`，不能藏入對戰加成。伺服器啟動時檢查，局中拒絕更換文明。
- `CommerceRules.lua` 商品欄位白名單為 `name`、`category`、`gamePassId`、`civilizationId`、`cosmeticId`；`category` 只接受 `civilization` 或 `cosmetic`。對應身份須有效，商品 ID 必須是有限的非負整數，非零 ID 不可重複。
- 文明商品不得同時指定 `cosmeticId`；造型商品不得同時指定 `civilizationId`。不允許其他能力、貨幣或加速欄位。
- `Commerce.purchase()` 目前只驗證並回傳目錄資料，**沒有建立購買提示、持有權驗證或發貨流程**。不能把規則模組當成完成的商店。

商業驗收需對每件商品做「免費／付費外觀、相同配置」對照，記錄初始資源、資源增量、全部成本、單位屬性、人口／佇列、科技效果與勝利條件。只要造型影響隱蔽、選取、碰撞或敵我／兵種辨識，就不能上架該版本。

## 2. 商店維持關閉：尚未配置任何商品

目前 `GameConfig.Commerce.enabled=false`、`catalog={}`，商品數為 **0**。規則允許開發草稿使用 `gamePassId=0`，但購買驗證會拒絕 ID 0。0 不是 Roblox 正式商品，也不代表已上架。三個現有文明河灣盟邦、旭日城邦、青林公國皆免費。

未配置期間，UI 可說明公平政策與展示免費文明；不得顯示假 Robux 價格、假購買成功、假擁有狀態或未能取得的商品。

未來若獲明確商品配置授權，按以下順序完成：

1. 在目標體驗的 Creator Hub 建立明確內容的通行證，保存真實 ID、圖示、名稱、說明與上架狀態；目前程式白名單使用 game pass，不把其他付款形式混成已支援。
2. 由 Roblox 商品資訊取得當前名稱／價格／可售狀態，避免寫死價格；檢查 ID 確實對應本作內容。官方文件說跨遊戲通行證銷售於 2026-05-30 起停用，因此不能拿其他體驗的 pass 冒充本作商品。[Roblox 官方 Passes](https://create.roblox.com/docs/production/monetization/passes)（查閱 2026-09-30）。
3. 由伺服器的 MarketplaceService 查 `UserOwnsGamePassAsync`，並在玩家加入及購買提示完成時更新合法的外觀使用權。官方要求通行證權利由伺服器處理；客戶端的「已買」訊息不能發貨。[Roblox 官方 Passes](https://create.roblox.com/docs/production/monetization/passes)（查閱 2026-09-30）。
4. 分別測未擁有、已擁有、付款取消、服務錯誤、重複提示、斷線重連與偽造持有訊息。失敗不得顯示成功；重複確認不重複發送任何權利。
5. 完成公平對照及正式服務證據後，才考慮開啟目錄。現有空目錄與 0 ID 測試不能代替以上步驟；本文件不會自行建立或上架商品。

## 3. 原創品牌與可審查素材

目前名稱「帝國鍛造坊」與三文明主題可作工作名稱。名稱、圖示、縮圖、旗幟和宣傳畫面以本作素材建立；不把工作名稱視為已完成的品牌認證。

發布內容逐項確認：

- 畫面使用本作實際地圖、UI、建築與單位；不取用 AOE2 標誌、官方美術、音樂或宣傳圖當本作素材。
- `Shared/Art.lua` 的原創幾何外觀可作缺模型替代。使用者保留的模板另列素材來源／可使用範圍，不因模板存在就宣稱全數原創；仍保留原模型，不擅自刪除。
- 商品圖和預覽必須與實際取得的外觀相符，並保留兵種、敵我、生命與施工等資訊的辨識。
- 標題／說明清楚寫「RTS 測試版」，列出實際支持的裝置、模式及未完成項目；不宣稱「Roblox 唯一 RTS」、「完整 AOE2」或已驗證的爆款。
- 設定、規則與玩家提示維持繁體中文。其他語言可後續實驗，不能把未翻譯的文字當已完成支援。

## 4. 正式存檔如何驗收

現有 `ProfileRules`／`ProfileStore` 儲存文明偏好及合格的純真人對戰結果，不儲存對局資源或永久能力。DataStore 名稱為 `RTS_Profile_v1`，玩家鍵為 `u_<UserId>`。Studio 預設停用，正式已發布伺服器才啟用；80 項 profile／analytics mock 檢查只能證明模擬流程。

最新純邏輯修正讓非大廳時載入的文明偏好等待下一次大廳；玩家任何有效明選含預設文明都優先，清除待套用值。延遲完成的讀取保留原選擇時間戳，避免舊伺服器壓過新伺服器偏好。這些情境已加入 80 項模擬回歸；沒有因此取得新的引擎或正式雲端證據。

Roblox 官方說同一體驗內各 place／伺服器可存取同一 DataStore，Studio 開啟 API 也會接觸相同資料。正式存檔測試應使用**獨立的測試體驗**，不能只是正式體驗內另一個 place；不在正式遊戲為測試開啟 Studio 存檔寫入。[Roblox 官方 Data stores](https://create.roblox.com/docs/cloud-services/data-stores)（查閱 2026-09-30）。

此處是後續正式服務驗收方式；建立／發布獨立測試體驗仍受第 7 節的禁止自動發布規則約束。已有明確可用的測試體驗後：

| 情境 | 執行與觀察 | 必須取得的證據 |
| --- | --- | --- |
| 首次進入／沒有資料 | 正式 Roblox 客戶端進入，等待 `ProfileStatus`；選文明，離開再進入。 | 正常初始化，文明偏好跨工作階段恢復；記錄伺服器、版本及讀寫狀態。 |
| 讀取延遲／玩家先選擇 | 載入晚於開局、觀戰或結算；另測載入前明選預設文明。 | 對局中不改文明；未明選者回大廳套用保存偏好一次；任何有效明選都優先，不被晚到偏好覆蓋。 |
| 資料已有歷史結果 | 讀取測試帳號已知資料，再做一次合格對局。 | 歷史值保留，只增加新結果，不把當局資源存入檔案。 |
| 同時更新 | 兩個測試伺服器對同一測試資料鍵各送不同結果 ID／偏好，再重新讀取。 | UpdateAsync 合併兩個增量；偏好有確定排序；沒有整份舊值覆蓋新值。 |
| 舊伺服器晚讀／晚寫 | 玩家離開 A 後進 B、選新偏好；再讓 A 的延遲讀取完成。 | A 保留原選擇時間，不提升舊偏好時間戳；B 新偏好保留，A 有效結果仍可合併。 |
| 結果重送／延遲 | 同一對局結果重試、重送及跨伺服器延遲後再次提交。 | 勝負只計一次，歷史去重日誌及時間界線有效；不同有效對局各計一次。 |
| 不合格戰績 | 單人練習、AI 對局、未成功開局、偽造客戶端勝利訊息。 | 不增加純真人 PvP 戰績；模組／伺服器權威拒絕偽造。 |
| 載入錯誤／未知版本 | 在隔離環境注入讀取失敗或不支援資料格式。 | `LoadFailed`，不覆寫既有雲端資料；UI 不宣稱已恢復或儲存成功。 |
| 儲存錯誤／重試 | 在隔離環境注入 UpdateAsync 失敗，恢復後重試，再重連。 | 顯示 `SaveFailed`，保留本工作階段增量，成功後沒有重複結果。失敗時 `ProfileLoaded=true` 只表示已有本機載入狀態，不能當儲存成功。 |
| 離開／關服 | 選文明或完成合格對局後離開／關閉測試伺服器，再進入。 | 完整增量可重新讀出；記錄關服期限與失敗日誌，不用「程式呼叫過」代替持久保存。 |

`UpdateAsync` 回呼不得等待，回傳 nil 會取消更新；目前用它保護損壞或不支援檔案。正式並行與失敗測試仍須證明服務行為。[Roblox 官方 Data stores](https://create.roblox.com/docs/cloud-services/data-stores)（查閱 2026-09-30）。測試結束保存去識別的結果／日誌，不將測試帳號資料或存取憑證貼進文件。

## 5. 正式分析如何驗收

現有 `Telemetry.lua` 的 `RTSFirstSession` 為**每次加入產生新 session ID 的漏斗**，不能解讀為永久只有一次的新玩家教學。步驟為 Joined→Queued→Started→FirstDelivery→FirstHouseCompleted→FirstUnitTrained；只在伺服器確認事件後記錄。另有 `RTSMatchStarted`、`RTSMatchCompleted`、`RTSMatchDeparted`，自訂欄位為 Mode、Civilization、Map。

Studio 預設停用。Roblox 官方也說漏斗與自訂事件只可由伺服器在已發布體驗送出，不能由 Studio 或客戶端送出；自訂事件圖表每日彙整，可能需最多 24 小時才出現。[官方 Funnel events](https://create.roblox.com/docs/production/analytics/funnel-events)、[官方 Custom events](https://create.roblox.com/docs/production/analytics/custom-events)（查閱 2026-09-30）。因此本輪的 mock／Studio COMPLETE 不代表 Dashboard 已有事件。

正式驗收流程：

1. 在已獲授權的測試體驗，以正式客戶端完成一次集合、開局、交貨、房屋完工與訓練；另一測試玩家在某一步退出。記錄版本、時間、OS、模式與行為預期。
2. 重複交貨、蓋屋、訓練，確認同一 session 的首次步驟不重送；重新加入應得到新 session。中途先訓練再蓋屋的玩家也要測，確認步驟順序設計不扭曲實際流程。
3. 看 Creator Hub 漏斗／Explore，核對名稱、步驟、分母、時間範圍、自訂欄位與預期退出點。分 OS 檢視，不從電腦是否支持觸控猜玩家正在用哪個裝置。
4. 核對自訂事件值：Started 的值 1 是次數；Completed／Departed 的值是經過秒數。平均／總和的含義不同，不把時長總和當完成局數。
5. 模擬服務失敗並確認只記錄錯誤，不影響資源、戰鬥與勝負。檢查事件頻率及偽造請求；client 沒有直接證明交貨或勝利的權利。

目前未實作完整版本／入口分群、所有介面點擊、首個選取／下令的時間、永久初次玩家標記及完整戰後分析。這些指標須補足事件或由受控觀察記錄，不能以現有六步漏斗自動推算。Dashboard 出數據後也須核對真實玩家行為，不能只看 API 無報錯。

## 6. 真實玩家實驗與指標

以下數值是本專案暫定驗證目標，不是 Roblox 官方門檻或現有測量結果。外部實驗目前未完成。

先請 10–20 位未玩過本作的人各自完成首局，觀察理解問題，不提前教快捷鍵；分別測桌面與真實手機。修正操作問題後再以同版本、入口、裝置的新增玩家群組量測。每個百分比附分子／分母；初期低於 100 名新玩家只判方向，不宣稱統計顯著或已證明市場。

| 指標 | 定義 | 暫定目標／使用方式 |
| --- | --- | --- |
| 首個有效指令時間 | 首次進入至伺服器接受第一道玩家指令，不含無效點擊。 | p75 ≤90 秒。現有分析尚無完整時間事件，先受控觀察，後補埋點。 |
| 五分鐘核心循環完成率 | 同一首次玩家完成選取、真實交貨、房屋完工、訓練及部隊操作。 | ≥70%。教學第五步只檢查步兵生成，不能代替實際下令。 |
| 首局完成率 | 真正開局玩家完成正常勝負或清楚結束流程；斷線、投降、沙盒另列。 | ≥60% 的暫定目標；不同模式分開分析，不能以離開後自動判負提高完成率。 |
| 快速對戰局長 | 有對手的快速模式開始到勝負。 | 中位數 12–18 分鐘是待測假說；目前無對手練習不能代替快速 PvP。 |
| D1／D7／D30 | 同首次進入 cohort 的玩家於相應日期返回。 | 先建立基線，再比較版本；必須等真實天數經過。沒有預設或捏造「已達標」數字。[官方 Retention](https://create.roblox.com/docs/production/analytics/retention)（查閱 2026-09-30）。 |
| 重開／朋友共玩 | 完成後再開局、與好友共同加入／玩；區分單人、FFA 與未實作的合作模式。 | 觀察是否增加 D1/D7 與首局完成；不把多人同步當同盟合作。 |
| 操作與效能 | 真手機完成核心操作、誤觸／指令取消、FPS／崩潰／記憶體。 | 真實低階裝置穩定 30 FPS 為初始目標；Studio 模擬不替代真機。 |
| 外觀購買意願 | 合法預覽後的意圖；正式商品上線後才有實際轉換。 | 同時觀察退出與公平反饋，不用攻擊／資源加成換轉換率。商品未配置時不得填實際營收。 |

A/B 實驗每次選一個主要變因，如提示、練習入口或結算重開；相同對局內所有人仍用相同公平規則。分清自然 Home、搜尋、邀請與廣告玩家；現有來源／版本埋點不足時，不能合併後宣稱改善。若核心理解或手機完成率低，先修操作再擴大宣傳。

## 7. 不自動發布、不覆寫原 place

[專案 AGENTS.md](../AGENTS.md) 明訂：

> 不自動發布 Roblox 體驗、不覆蓋現有 place 檔；輸出到 build，原始碼變更前保留備份或版本紀錄。

因此本輪工作只準備原始碼、文件、測試與 `build` 輸出，不代使用者公開發布體驗、建立／上架正式商品或覆寫原 place。本文件不是發布授權；後續只有使用者明確變更此限制，才可執行對應發布動作。

發布前先交付可審查版本與 [ROADMAP.md 的 G01–G12](ROADMAP.md)：對應最新原始碼的 build、Studio 日誌、真實手機／雙人／經濟／戰鬥／勝負證據、原模型保留、未完成清單、品牌素材與公平商業設定。16:30 桌面 18／20／36 項 COMPLETE 支持較早快照；16:40–16:41 iPhone XR 橫向 Studio Release 19／Touch 33／Construction 36 項 COMPLETE 支持其當時版本。證據見 [latest-release-touch-results.txt](../tests/latest-release-touch-results.txt)。
